# 01 · 总体架构：rsolver 是怎么工作的

> 阅读对象：想理解 `rsolver` 整体运作方式的人。
> 前置：无。本文所有名词都从零解释。

---

## 1. rsolver 是什么

`rsolver` 是《格里米斯的工匠》的 **Rust 求解器二进制**。它是一个**标准命令行程序**：

- **输入**：从标准输入（stdin）或命令行参数指定的文件读取**谜题 JSON**；
- **处理**：把 JSON 解析成内部模型，交给一串求解算法；
- **输出**：把结果序列化成**题解 JSON** 写到标准输出（stdout）。

```
$ rsolver puzzle.json > solution.json
$ cat puzzle.json | rsolver > solution.json
$ cat p1.json p2.json | rsolver --batch   # 多行输入 → 逐行输出
```

> `--batch` 模式（2026-08-06 新增）：从 stdin **逐行读**多份紧凑谜题 JSON，逐题求解、
> **逐行输出**一份题解 JSON（1 输入行 ↔ 1 输出行；坏行输出 `solved:false` 继续）。
> Python `RustSolver.solve_batch` 借此复用一个子进程批量求解（**每题独立预算**：逐行
> `select` 读，超时只截断该题与后续题）。JSON 模型、构建与序列化在 `io` 模块
> （`src/io.rs`），`main.rs` 只做 stdin/argv/stdout 调度。
>
> **每题预算 thread**（2026-08-08 修复）：`main.rs::resolve_timeout_ms` 读
> `RSOLVER_TIMEOUT_MS` 环境变量（默认 30 000，下限 1 000），`RustSolver` 的
> `_subprocess_env` 从 `--timeout` 设入，`solve_json_line(line, timeout_ms)` 透传——
> 原 `solve_json_line` 硬编码 30s，`--timeout 40` 根本到不了 Rust 搜索。修复后每段
> 求解器（aog/pieces/backtrack/rose）各拿完整 `timeout_ms` 作 deadline（unit budget）。
> 同步移除了 `solver::solve` 里 rose 阶段的 `ROSE_TIMEOUT_MS = 30_000` clamp（原
> `.min(ROSE_TIMEOUT_MS)` 即使 `--timeout 40` 仍把 rose 封顶 30s），让 `timeout_ms`
> 成为 rose 唯一上限。
>
> **batch 连带超时已缓解**：原硬编码 30s × unit budget（每段 30s = 最多 90s/题）远超
> Python 期望的 `timeout×3`，一题 runaway 会连带同批后续题判超时。透传后每题
> `solve_json_line` 在 `timeout_ms` 处停住，串行循环每轮时间有界；`RustSolver._wall_budget`
> 再给 `RUST_PARTS(4)× unit × 1.2` slack 墙钟吸收 `-j N` CPU 争抢。`--batch N` 现可用于精确验证。

> Python 侧的 `src/solver/rust_solver.py` 就是起一个 `rsolver` 子进程、
> 喂 JSON、读回 JSON。所以「Rust 求解器」和外界唯一的边界就是**这份 JSON**。

## 2. 主流程：从 JSON 到 JSON

入口在 `src/main.rs`（很薄，IO 逻辑在 `src/io.rs`）。单题全流程如下：

```
┌─────────────────────────────────────────────────────────────────────┐
│ main()                                                               │
│  1. 读入 JSON 文本（stdin 或参数文件）                                 │
│  2. io::parse_puzzle → serde_json 反序列化 → PuzzleJson →             │
│     build_puzzle → Puzzle（内部领域模型）                              │
│        · 逐格建 Cell（含 number/symbol/compass/fence/shape_pattern）  │
│        · 逐边建 Edge（is_boundary / constraint）                      │
│        · 逐顶点建 Vertex（watchtower）                                │
│        · 收 shape_pool、rules、outer_boundaries                      │
│        · 任何坐标越界 / 边不合法 → 直接报错退出                          │
│  3. solver::solve(&puzzle, timeout_ms)  ← resolve_timeout_ms() 读      │
│     RSOLVER_TIMEOUT_MS（默认 30000，下限 1000），unit budget 各段共享    │
│  4. io::solution_to_json_text → 序列化 → 写 stdout                    │
└─────────────────────────────────────────────────────────────────────┘
```

`--batch` 模式把第 2~4 步放进 `io::solve_json_line` 逐行跑（1 输入行 ↔ 1 输出行）。

`PuzzleJson`（I/O 模型，`io.rs:22-107`）和 `Puzzle`（领域模型，`types.rs:150-167`）
是两套结构。前者完全贴合磁盘上的 JSON 形状（`edges[]` 是平铺列表、`grid{height,width}`
等），后者是为求解优化过的二维数组形态（`cells[r][c]`、`h_edges[r][c]`、`v_edges[r][c]`）。

### 2.1 一份输入 JSON 的骨架

```json
{
  "version": "1.0",
  "grid": { "height": 4, "width": 5 },
  "cells": [
    { "row": 0, "col": 0, "number": 3 },
    { "row": 0, "col": 1, "symbol": "A" },
    { "row": 1, "col": 2, "blocked": true },
    { "row": 2, "col": 3, "compass": { "up": 2, "down": 0, "left": null, "right": 1 } }
  ],
  "edges": [
    { "r1": 0, "c1": 0, "r2": 0, "c2": 1, "is_boundary": true },
    { "r1": 1, "c1": 2, "r2": 2, "c2": 2, "constraint": { "type": "difference", "value": 2 } }
  ],
  "vertices": [ { "row": 1, "col": 2, "watchtower": 3 } ],
  "outer_boundaries": [],
  "rules": [ { "type": "precise", "params": { "area": 3 } } ],
  "shape_pool": [ [[0,0],[1,0],[1,1]] ]
}
```

> 完整字段约定见 [02-数据结构](02-数据结构.md) 和 `main.rs` 的 `*Json` 结构体。

## 3. 核心：`solve()` 求解器路由

`src/solver/mod.rs:12` 的 `solve()` 是**大脑**。它按固定优先级尝试 5 个求解器：

```
solve(puzzle, timeout_ms)
│
├─ 特殊情况：无可填格 → 直接返回「已解决」（空区域集）
│
├─ ① AoG DFS ────────────────────────────────────────────────
│    ├─ 预算：rose 能力题 3s，否则给满 timeout_ms
│    ├─ 命中 → build_solution_trusted（内部校验权威，不再复查）
│    └─ 未命中且是纯 rose 题 → ② Rose（预算 = 剩余 timeout_ms，无 30s clamp）
│         ├─ puzzle_piece 题 → 预钉 shape_pattern 区域（puzzle_piece_pin）
│         │   再 region_match 求剩余，m'=1 走 try_single_region 快速路径
│         └─ region_match（精确覆盖）→ 失败回退 rose_growth（贪心生长）
│
├─ ③ EdgeCSP（后置 fallback）── is_edge_csp_capable 才走 ────────
│    ├─ 边约束密集题（ring/brick/watchtower/compass/inequality/difference，
│    │   且所有规则 ⊆ {上述 + area/precise/range}）
│    └─ 命中 → build_solution（全量 validate 复查，非 trusted）
│
├─ 路由判定：
│    ├─ 有 shape_pool / 面积数字线索 / 强罗盘线索
│    │      → ④ Pieces（DLX 精确覆盖）
│    └─ 否则 / ④ 失败 → ⑤ Backtrack（区域回溯）
│
└─ 全失败 → 返回 { solved:false, error_message:"No solution found" }
```

### 3.1 五段求解器的定位（一句话版）

| # | 求解器 | 一句话定位 | 擅长的规则 | 代码 |
|---|---|---|---|---|
| ① | **aog** | C++ 参考求解器的 1:1 移植，形状放置 + 海量剪枝 | 绝大多数官方题 | `solver/aog/*` |
| ② | **rose** | 专门对付 aog 超时的纯玫瑰窗题 | `rose_window` | `solver/rose/*` |
| ③ | **edge_csp** | 边变量 CSP（三态边 + 传播-探测-回溯） | `ring`/`brick`/`compass`/`inequality`/`difference` | `solver/edge_csp/*` |
| ④ | **pieces** | 把「放形状」建模成精确覆盖，用 DLX 求解 | `shape_pool` / 面积数字 / 罗盘 | `solver/pieces.rs` |
| ⑤ | **backtrack** | 逐格归属的朴素回溯 | 通用兜底 | `solver/backtrack.rs` |

### 3.2 时间预算（重要细节）

`mod.rs` 的注释明确说明：**`timeout_ms` 是「每段求解器各自一份」的预算**，
而不是五段共享。也就是说：

- aog 拿到完整 `timeout_ms`（玫瑰窗题则缩到 `AOG_ROSE_BUDGET_MS = 3_000ms`，
  因为 aog 对无尺寸约束玫瑰窗题会长时间挂死）；
- rose 拿到 `剩余 timeout_ms`（2026-08-08 移除旧的 30s clamp——原 `min(剩余, 30s)`
  让 `--timeout 40` 的 rose 阶段永远只拿 30s，与 unit budget 哲学不一致）；
- edge_csp / pieces / backtrack 又各自拿到 `timeout_ms`。

> 这解释了为什么 Python 侧要给子进程 `RUST_PARTS(4)` 倍的墙钟时间——因为子进程内部
> 可能依次花掉 timeout + timeout + timeout + timeout。`RustSolver._wall_budget` 给
> `RUST_PARTS(4) × timeout × 1.2` slack 吸收 `-j N` 下的 CPU 争抢。`timeout_ms` 本身由
> `RSOLVER_TIMEOUT_MS` env var thread 进来（`main.rs::resolve_timeout_ms`，默认 30 000，下限 1 000）。

### 3.3 判定公式

`solve()` 里用几个辅助函数决定走不走 pieces：

```
has_shape_pool   = !puzzle.shape_pool.is_empty()
has_area_clues   = 存在任意 cell.number（面积数字）
has_compass_clues= 存在「3 个方向以上」或「条带型」的罗盘
                  （strip = 左右都为0 或 上下都为0）

走 pieces ⟺ has_shape_pool || has_area_clues || has_compass_clues
否则/失败 → backtrack
```

`is_rose_capable` 判定是否给 rose 机会（`mod.rs:238-244`）：

```
有 rose_window 规则，且没有 same / different 规则  → true
```

## 4. 答案是怎么被构建和把关的

五个求解器解完都产出 `Vec<RegionInfo>`（区域列表）。`solve()` 调用**两种**答案构建器：

| 构建器 | 触发时机 | 行为 |
|---|---|---|
| `build_solution_trusted` | aog 命中 | 信任 aog 内部校验，直接把规则全标 true，**不再复查** |
| `build_solution` | rose / edge_csp / pieces / backtrack 命中 | ① 检查**不跨越预画边界**；② 跑 `solver/validate.rs` 全量规则复查（覆盖全部 22 规则，`constraints.rs` 已删）；③ 有一条规则没过就标 unsolved |

```
build_solution(regions, start, puzzle)
│
├─ regions_respect_boundaries()？   ← 每段求解器产出都要过
│     「预画边界两侧必须是不同区域」，否则拒绝
│
├─ solver::validate::validate()      ← 全 22 规则复核
│
└─ solved = 每条规则都通过
```

> **关键不变量**（CLAUDE.md 反复强调）：路由**独立复核**每个答案。aog 内部校验
> 被视为权威（信任），其余求解器的答案则必须过 `solver/validate.rs` + 边界尊重检查。
> 任何改动都不能破坏「错误答案无法通过校验链」。

### 4.1 完整的双重保险

```
                ┌─ aog 命中 → 内部校验权威（solver/validate.rs 仍在出口复核一次）
  5 个求解器 ──┤
                └─ rose/edge_csp/pieces/backtrack → 边界尊重 + validate.rs 复查
                          │
                          ▼
                Python 侧 Router 再 IndependentValidator 全量复核（最终保险）
```

注意到 `aog/mod.rs:32-41`：aog 找到解后仍会调用 `validate::validate` 复核一次才返回，
所以「aog 信任」其实还有一层内层自检。

## 6. 数据流：一个具体谜题走完全程

以一份 5×4、形状池规则的题（官方 0095）为例：

```
① main.rs 读 JSON ─► PuzzleJson（平铺数组）
② build_puzzle ────► Puzzle { cells[4][5], h_edges[4][4], v_edges[3][5], ... }
③ solve() ─────────► aog 构建 AoGCore（把 Puzzle 编码进 (2h+5)×(2w+5) 位域网格）
④ aog dfs() ───────► 找到解 → extract_regions → Vec<RegionInfo>
⑤ validate 复核 ───► 通过
⑥ build_solution_trusted → SolutionJson（regions + rule_results 全 true）
⑦ stdout ──────────► 题解 JSON
```

题解 JSON 形如：

```json
{
  "solved": true,
  "steps_taken": 0,
  "elapsed_ms": 42,
  "error_message": null,
  "regions": [
    { "region_id": 1, "cells": [[0,0],[1,0],[2,0]], "area": 3,
      "shape": [[0,0],[1,0],[2,0]],
      "normalized_shape_key": "(0,0)(1,0)(2,0)", "matched_shape_name": null }
  ],
  "rule_results": { "shape_pool": true },
  "solver": "aog",
  "attempts": [
    { "solver": "aog", "status": "success", "elapsed_ms": 42, "note": null }
  ]
}
```

> `steps_taken` 在 Rust 侧恒为 0（Python 才统计步数）。`elapsed_ms` 是内部耗时。
> `rule_results` 对 aog 命中是全 true，对其它求解器是 `solver/validate.rs` 的复查结果。
> `solver` 标出是哪个模块解的：`aog` / `rose` / `pieces` / `backtrack`；错误、空盘、超时
> 等占位解为空串。`benchmark_rust_solver.py` / `benchmark_rust_solver.py` 用它把每个结果归到
> 具体模块（`via=...`），便于定位"哪个求解器对哪些题有短板"。
>
> `attempts`（doc 23）是 **per-module 求解链**：分派处每考虑一个模块（含 `not_attempted`）
> 就 push 一条 `{solver, status, elapsed_ms, note}`。`status` 六态：`success` / `timeout` /
> `exhausted`（预算内搜完无解）/ `validation_failed`（找到候选但 `validate` 拒绝，原先被
> `None` 吞掉）/ `not_attempted` / `error`。`elapsed_ms` 是该模块自身 wall-clock（非累计）。
> 多模块题如 C4-1 的链是 `aog:timeout → rose:success`——这层信息以前完全不可见。
> `attempts` 为新增可选字段（`skip_serializing_if = Vec::is_empty`），旧消费者不解析即忽略。

## 7. 关键设计决策备忘

1. **aog 是 1:1 移植**：`aog/` 每个函数几乎都能在 `third_party/AoG_Solver` 的 C++
   源码里找到对应。目的是**行为完全对齐**，官方题结论可交叉验证。
2. **rose 单独成模块**：aog 移植得很忠诚，反而暴露了它对无尺寸约束玫瑰窗题的
   短板，所以单独写了 rose 求解器来兜。
3. **预画边界是全求解器硬约束**：aog 把它编码成 `LINE_BLOCK`；pieces/backtrack
   不感知边界，所以 `build_solution` 里的 `regions_respect_boundaries` 是**最后一道闸**。
4. **答案可被拒绝**：一个求解器「找到解」≠ 接受——要过验证链才算数，否则路由
   继续尝试下一个求解器。
