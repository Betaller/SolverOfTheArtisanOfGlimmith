# 02 · 数据结构：一个谜题在 Rust 里长什么样

> 阅读对象：想了解内部数据表示的人。
> 前置：01 总体架构。

一个谜题在 `rsolver` 里有**两层表示**：

1. **领域模型**（`types.rs` 的 `Puzzle`）——贴近 JSON、贴近人类理解。
2. **加边像素网格**（`aog/types.rs` 的位域 `Vec<Vec<u32>>`）——为性能优化，
   是 aog 求解器真正操作的盘面。

本文把两层都讲清楚，并给出坐标换算与位域编码表。

---

## 1. 领域模型层（`types.rs`）

### 1.1 `Puzzle` —— 一个谜题

```rust
pub struct Puzzle {
    pub height: usize,                        // 行数 H
    pub width:  usize,                        // 列数 W
    pub cells:  Vec<Vec<Cell>>,               // cells[r][c]，H×W
    pub h_edges: Vec<Vec<Edge>>,              // 水平边 [r][c]：连接 (r,c) 与 (r,c+1)
    pub v_edges: Vec<Vec<Edge>>,              // 垂直边 [r][c]：连接 (r,c) 与 (r+1,c)
    pub vertices: Vec<Vec<Vertex>>,           // 内部顶点 (r,c)：四格共用角
    pub rules: Vec<Rule>,                     // 全局规则列表
    pub shape_pool: Vec<Shape>,               // 形状池
    pub outer_boundaries: Vec<[usize; 4]>,    // 外边框线段（round-trip 用）
}
```

```
Puzzle 的几何视图（以 3×3 为例）：

   外边框 ◄──────────────────────────────────►

   ┌──────┬──────┬──────┐
   │ Cell │ Cell │ Cell │      h_edges[0][0]: (0,0)-(0,1) 水平边
   │(0,0) │(0,1) │(0,2) │      h_edges[0][1]: (0,1)-(0,2)
   ├──────┼──────┼──────┤      v_edges[0][0]: (0,0)-(1,0) 垂直边
   │ Cell │ Cell │ Cell │
   │(1,0) │(1,1) │(1,2) │      vertices[0][0]: (0,0)(0,1)(1,0)(1,1) 四格共用角
   ├──────┼──────┼──────┤
   │ Cell │ Cell │ Cell │
   │(2,0) │(2,1) │(2,2) │
   └──────┴──────┴──────┘

   h_edges 尺寸：H × (W-1)；v_edges 尺寸：(H-1) × W；vertices 尺寸：(H-1) × (W-1)
```

### 1.2 `Cell` —— 一个格子

```rust
pub struct Cell {
    pub row: usize,                 // 行
    pub col: usize,                 // 列
    pub number: Option<i64>,        // 面积数字线索（area 规则）
    pub symbol: Option<String>,     // 玫瑰窗符号（rose_window 规则）
    pub blocked: bool,              // 障碍格（不参与划分）
    pub compass: Option<CompassClue>,     // 罗盘线索
    pub fence_pattern: Option<Shape>,     // 围栏图案（3×3 小图）
    pub shape_pattern: Option<Shape>,     // 拼块图案（puzzle_piece 规则）
    pub region_id: Option<usize>,   // 求解期归属的区域号
}
```

> `Cell::assigned()` = `region_id.is_some()`；`Cell::fillable()` = `!blocked`。

### 1.3 `CompassClue` —— 罗盘

```rust
pub struct CompassClue {
    pub up: Option<i64>,    // 北方（行更小）的同区域格数；None = 无限制
    pub down: Option<i64>,  // 南方
    pub left: Option<i64>,  // 西方
    pub right: Option<i64>, // 东方
}
```

> JSON 里 `null` / 负数会被 `normalize_compass_value` 归一化为 `None`（无限制）。

### 1.4 `Edge` —— 一条相邻边

```rust
pub struct Edge {
    pub is_boundary: bool,                // true = 预画分界线，两侧必须不同区域
    pub constraint: Option<EdgeConstraint>, // 边约束（双子/异生/不等号/差值）
}
```

### 1.5 `EdgeConstraint` 与 `EdgeConstraintType`

```rust
pub struct EdgeConstraint { pub ctype: EdgeConstraintType, pub value: Option<i64> }

pub enum EdgeConstraintType {
    Heterogeneous,   // 异生 delta   —— 两侧形状不同
    Homogeneous,     // 双生 gemini  —— 两侧形状相同
    Inequality,      // 不等号       —— 两侧面积大小关系（value==1 → 首端更大）
    Difference,      // 差值         —— |面积差| == value
}
```

### 1.6 `Vertex` —— 顶点（望塔）

```rust
pub struct Vertex { pub watchtower: Option<i64> }   // 1..=4，接触该顶点的区域数
```

### 1.7 `Shape` 与归一化

```rust
pub type Shape = Vec<[usize; 2]>;   // 若干 (row, col)，归一化到原点

pub fn normalize(shape) { /* 平移到 (0,0)，再排序 */ }
pub fn canonical_key(shape) -> String { /* 输出 "(r,c)(r,c)..." 字符串 */ }
```

> `polyomino.rs::transforms` 产出**自由多连块**的全部 8 种对称（4 旋转 × 2 镜像），
> 并去重——即“旋转和镜像视为同一形状”。`shapes.rs::dihedral_key`（`shapes.rs:32`）
> 用同样的 8 变换取字典序最小者作为**形状的规范标识**——这是全 solver 唯一的
> 实现（aog / pieces / backtrack / rose 与验证器共用，见 08）。

> `shapes.rs` 还集中了另外四个曾被多处复制的形状/面积辅助：`is_rectangle`
> （实心矩形判定）、`collect_pool_shapes`（形状池双来源收集）、`area_bounds`
> （precise/range + 罗盘派生面积上下界）、`rose_symbol_types`（玫瑰窗符号类型）。

### 1.8 `Rule` —— 全局规则

```rust
pub struct Rule {
    pub ctype: String,                                   // 如 "precise" / "range"
    pub params: HashMap<String, serde_json::Value>,      // 如 {"area": 4}
}
```

### 1.9 `Solution` 与 `RegionInfo` —— 题解

```rust
pub struct Solution {
    pub solved: bool,
    pub steps_taken: u64,            // Rust 恒 0
    pub elapsed_ms: u64,
    pub error_message: Option<String>,
    pub regions: Vec<RegionInfo>,
    pub rule_results: HashMap<String, bool>,
}

pub struct RegionInfo {
    pub region_id: usize,
    pub cells: Vec<[usize; 2]>,      // 该区域的格子坐标
    pub area: usize,                 // 面积 = cells.len()
    pub shape: Shape,                // 归一化到原点的形状
    pub normalized_shape_key: String,
    pub matched_shape_name: Option<String>,   // 若匹配形状池中的命名形状
}
```

## 3. 加边像素网格：aog 的盘面表示

aog 求解器不直接用 `Puzzle`，而是把它**编码进一个放大了约 2 倍的二维 `u32` 数组**，
`(2H+5)×(2W+5)`（`aog/core.rs:644-652`）。这样格子、边、顶点都能放进**同一个数组**，
信息局部性好、缓存友好——这是 C++ 参考求解器的经典设计。

### 3.1 坐标换算

逻辑坐标（行/列 `x, y`，从 1 开始）↔ 像素网格坐标（`px, py`）：

```
to_puzzle_x(x) = 2x + 1        // 格子中心
to_puzzle_y(y) = 2y + 1

像素网格中：
  奇×奇           = 格子中心     （存 AREA_* 位域）
  奇偶/偶奇       = 相邻格子之间 = 边（存 LINE_* 位域）
  偶×偶           = 顶点（四格共用角，存 VERTEX_RADAR_BIT）
  外围 5 圈       = 边框哨兵     （LINE_BLOCK，防止越界）
```

以 1×2 的迷你盘面（逻辑格 (1,1)、(1,2)）为例：

```
像素网格 = (2*1+5)=7 行 × (2*2+5)=9 列。有效区是 行 2..=4、列 2..=6。

col:     0  1  2  3  4  5  6  7  8
row 0:   B  B  B  B  B  B  B  B  B
row 1:   B  B  B  B  B  B  B  B  B
row 2:   B  B  V  E  V  E  V  B  B   ← 顶点/边 行
row 3:   B  B  E  A  E  A  E  B  B   ← 格行：A=格(1,1)  A=格(1,2)
row 4:   B  B  V  E  V  E  V  B  B
row 5:   B  B  B  B  B  B  B  B  B
row 6:   B  B  B  B  B  B  B  B  B

  A = 格子中心（奇×奇，AREA_*）
  E = 边（奇×偶 / 偶×奇，LINE_*）
  V = 顶点（偶×偶，VERTEX_RADAR_BIT）
  B = LINE_BLOCK 哨兵（外圈防越界）
```

> 格 (1,1) 中心在像素 (3,3)（`to_puzzle_x(1)=3`）；两格之间的水平边在 (3,4)；
> 四格共用角顶点在 (2,2)/(2,4)/(2,6)/(4,2)/(4,4)/(4,6)。

> 具体到 `build`：格 `(r,c)` 的逻辑坐标是 `(r+1, c+1)`，像素坐标
> `px=2(r+1)+1=2r+3`、`py=2c+3`（`aog/core.rs:663-668`）。
> 望塔顶点 `(r,c)`（格 (r,c) 的右下角）像素坐标 `(2r+4, 2c+4)`（`aog/core.rs:762-764`，
> 有一整段注释解释为何不是 `2r+2,2c+2`——那是曾经的一格偏移 bug）。

### 3.2 位域编码表

数组元素是 `u32`，不同比特段存不同含义。按“什么元素在哪个位置”分为三类：

**格子位域（AREA_*）**：

| 常量 | 掩码 | 位移 | 含义 |
|---|---|---|---|
| `AREA_NORMAL` | 0 | — | 普通未填格 |
| `AREA_BLOCK` | `0x8000_0000` | — | 障碍格（阻塞） |
| `AREA_PALISADE_INDEX_BIT` | `0x7000_0000` | 28 | 围栏类型（1..=6） |
| `AREA_SHAPE_INDEX_BIT` | `0x0f00_0000` | 24 | 拼块形状目录索引（低 4 位） |
| `AREA_SHAPE_SIZE_BIT` | `0x00ff_0000` | 16 | 面积数字（1..=255） |
| `AREA_SLASH_INDEX_BIT` | `0x0000_f000` | 12 | 玫瑰窗符号类型索引 |
| `AREA_COMPASS_ENABLE` | `0x0000_0800` | — | 该格带罗盘 |
| `AREA_SYMBOL_BIT` | `0x0000_0004` | — | 该格带符号字符串 |

**边位域（LINE_*）**：

| 常量 | 掩码 | 含义 |
|---|---|---|
| `LINE_NORMAL` | 0 | 普通边 |
| `LINE_BLOCK` | `0x8000_0000` | 分界线（强制两侧不同区域 / 预画边） |
| `LINE_DIFFERENT` | `0x4000_0000` | 异生：两侧形状不同 |
| `LINE_EQUAL` | `0x2000_0000` | 双生：两侧形状相同 |
| `LINE_SMALLER` | `0x1000_0000` | 上/左区域更小 |
| `LINE_LARGER` | `0x0800_0000` | 上/左区域更大 |
| `LINE_SIZE_DIFF_BIT` | `0x000f_0000` | 差值（存 `value+1`，见 03） |

**顶点位域**：

| 常量 | 掩码 | 位移 | 含义 |
|---|---|---|---|
| `VERTEX_RADAR_BIT` | `0x0000_000f` | 0 | 望塔值（1..=4） |

### 3.3 求解中间态：`SOLVE_AREA_BIT`

在搜索中，aog 在 `sp`（solve puzzle）数组里填 `index | (shape_index << 16)`：

| 常量 | 掩码 | 含义 |
|---|---|---|
| `SOLVE_AREA_BIT` | `0x0000_ffff` | 低 16 位：区域号 |
| `SOLVE_AREA_SHAPE_INDEX_BIT` | `0xffff_0000` | 高 16 位：形状目录索引 |

```
一个已填格的值 = 0x00AB_0003 表示：形状目录索引 0xAB，区域号 3
未填格 = AREA_NORMAL (0)；障碍格 = AREA_BLOCK
```

## 4. 两层表示如何互相转换

```
 JSON ──► PuzzleJson ──build_puzzle──► Puzzle（领域模型）
                                         │
                             aog::AoGCore::build(puzzle, deadline)
                                         ▼
                                   位域像素网格 puzzle / sp
                                        │
                             search::dfs(...) 求解
                                        │
                             aog::extract_regions（把 sp 读回 (r,c) 列表）
                                        ▼
                                   Vec<RegionInfo>
```

转换要点：

- `Puzzle` → 位域：`aog/core.rs::build` 逐格/逐边/逐顶点搬数据，
  并做“哪些规则激活”的裁剪（只有激活的规则才编码对应线索）。
- 位域 → `RegionInfo`：`aog/mod.rs::extract_regions` 遍历可填格，
  按低 16 位区域号分桶，再把像素坐标还原成 `(r,c)`（`to_puzzle_x` 的逆运算）。

## 5. 为什么需要位域网格？

| 维度 | 领域模型 | 位域网格 |
|---|---|---|
| 内存布局 | `Vec<Vec<Cell>>`，Cell 很大（含 Option<String>） | 单一 `u32` 数组，紧凑 |
| 访问 | 多次解引用 | 直接索引 |
| 表达力 | 清晰 | 格子/边/顶点交织在一个数组 |
| 谁在用 | 全部求解器读线索 | 只有 aog |

> `docs/重构/data-structures.md` 有更完整的建模方式对比表，可交叉参考。
