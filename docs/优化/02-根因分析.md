# 02 · 根因分析

> 本文把 [01-内存现状与实测基线](01-内存现状与实测基线.md) 的实测现象逐一归因到代码，
> 并对照 C++ 参考实现 `third_party/AoG_Solver`，说明「哪些是参考缺陷被复刻、哪些是 Rust 移植引入」。

---

## 1. 🔴 aog 自由形状搜索：形状库无界增长

### 1.1 现象

无尺寸约束题（无 `precise` / `range` / `shape_pool` / `area` / `puzzle_piece` 规则）在
8×10 以上盘面、aog 无法 30s 内解出时，RSS 以 **~600 MB/s** 线性增长，最终 5~7 GB，且不回落。

### 1.2 触发条件链

1. **`shape_size_upper_bound` 无约束时 = 棋盘可填格数**（`aog/core.rs:898-899`）：
   ```rust
   if core.config.shape_size_upper_bound < 1 {
       core.config.shape_size_upper_bound = empty_area_cnt as usize;  // 最大 256
   }
   ```
2. **`dfs` 对每个 size 枚举自由多连块**（`aog/search.rs:1301-1324`）：
   尺寸下界~上界逐档调用 `place_non_predifined_shape`。自由多连块数量随尺寸**指数增长**
   （size=80 的自由多连块数远超可观测宇宙原子数），搜索永远收敛不了。
3. **搜索中发现的新形状全部入形状库**（`aog/search.rs:246`）：
   ```rust
   core.shapes_insert(&mut shape_buf, shape_size);   // 每个叶子节点都触发
   ```
4. **`shapes_insert` 对每个唯一形状类插入最多 8 个旋转/镜像**（`aog/core.rs:168-192`），
   每次插入都向三张结构累积：
   - `shapes: Vec<Shape>`（`Shape{nodes: Vec<Node>, digest, preview: Vec<u32>}` 每项两次堆分配）
   - `node_to_shape_index: HashMap<(i32,i32), Vec<usize>>`（对每个节点 push）
   - `shape_digest_index: HashMap<u32, Vec<usize>>`

### 1.3 与 C++ 参考实现的关系

| 方面 | C++ AoG_Solver | Rust rsolver |
|---|---|---|
| `shapes` | `std::vector<Shape>`，同样无界增长 | `Vec<Shape>`，同样无界（忠实复刻） |
| `mark_skip` | `mark_skip_shape[MARK_SKIP_CAP=262144]` **固定数组**，超限**越界读**（UB） | `Vec<bool>` 按需 resize（`search.rs:987-989`），安全但无上限 |
| 超时 | **无 deadline**，靠外层脚本 kill | 移植加了 30s deadline（`search.rs:113` / `:978`） |
| 结论 | 形状库无界是参考实现自身缺陷 | Rust 用安全内存把它从「越界崩溃」变成「内存继续涨」 |

**本质**：这不是 Rust 移植引入的 bug，而是**参考实现的缺陷被忠实复刻**，且 Rust 的
安全实现让缺陷表现为可观察的内存爆炸（C++ 在多数环境下直接段错误或慢到被脚本杀掉）。

### 1.4 为什么 30s deadline 没挡住

- deadline 检查点：`place_non_predifined_shape` 每 4096 步（`search.rs:113`）、`dfs` 每 256 个形状
  （`search.rs:978`）。粒度本身够密。
- 但当 RSS 冲到数个 GB 后系统进入 **swap 抖动**，单次检查耗时被放大，进程实际上无法按时到达
  检查点；且 30s 内已积累 6.8 GB（600 MB/s × 30s），即使按时停住，**已经占用的内存也不会释放**
  （形状库全程驻留，见 [04-内存泄露审计](04-内存泄露审计.md) §3.1）。

## 2. 🔴 rose region_match：候选 `visited` 无上限 + 多层克隆

### 2.1 现象

C4-2（10×11 玫瑰窗，★▲● 各 6）peak 102 MB，15s 未解出。

### 2.2 机制

1. **`CANDIDATE_CAP = 20000` 只限制结果数，不限制去重集**（`region_match.rs:16,67`）：
   ```rust
   while let Some((current, frontier, syms)) = queue.pop_front() {
       if results.len() >= CANDIDATE_CAP { break; }   // 只停 results
       ...
       visited.insert(new_fs.clone());                 // visited 无上限
   }
   ```
   BFS 在「攒够 20000 个完整候选」前会探索**数百万**中间连通子集，全部留在
   `visited: HashSet<CellSet>` 与 `queue` 里。`CellSet` 每次操作都要克隆 `Vec<u64>`。
2. **多层克隆放大**：
   - `all_candidates` 持有每个 seed 的 20000 个候选（`:347`）。
   - `candidates_by_size` 把每个候选再 clone 一份（`:412`）。
   - `match_regions_mrv` 每个面积组合 `sized.push(list.clone())` 再克隆（`:448`）。
3. **面积组合爆炸**：`enum_area_combos_bounded` 枚举所有区域面积分配（`:419`），
   每组合触发一次整表 `clone` + 一次 MRV 匹配；组合多时克隆 churn 放大。

### 2.3 为什么 168-rose-match7（16×16）反而秒解

该题带 `range` 尺寸约束 → `region_size_bounds` 生效 → 候选在 `generate_all_candidates` 后
按尺寸范围**提前剪枝**（`:374-380`），且 `can_partition` 可达性过滤砍掉大量候选（`:385-396`）。
**没有尺寸约束的玫瑰窗题才是病态区**——这也是 aog 对「无尺寸约束玫瑰窗」超时、
rose 被设计来兜底它的原因（`solver/mod.rs:39-69`）。

## 3. 🟠 aog `Pools` 固定预分配 100 层

### 3.1 现象

所有走 aog 的题（含 6×6 小盘）常驻 ~3.6 MB 的 `Pools`。占 A1-1 总 RSS（5.6 MB）的约 2/3。

### 3.2 机制

`Pools::new(depth)` 一次性 `Vec::push` 100 个 `RefCell<PlaceLevel>`（`aog/types.rs:297-313`），
`MAX_DFS_DEPTH = 100`（`:50`）。每个 `PlaceLevel` 是十几个**定长数组**（`current_shape[256]`、
`expand_candidates[774]`、`rectangle_*[256]×4`、`stack_*[258]×6` 等，`:226-253`），单层 ~36 KB。
DFS 实际深度远小于 100，但 100 层全量预分配。

### 3.3 与 C++ 的关系

C++ `mark_skip_pool[MAX_DFS_DEPTH][MARK_SKIP_CAP]` 也是全量静态数组（`dfs.cpp:31`），
但那是 `2×262144×...` 字节的**静态存储**，不占堆、进程启动即存在；Rust 用 100×36KB 堆分配。
两者都是「按最大深度预分配」，但 C++ 无堆开销，Rust 在堆上。

## 4. 🟡 backtrack `HashMap` 状态（次要）

- `BacktrackState.cell_to_region: HashMap<(usize,usize),usize>`（`backtrack.rs:56`）——
  格子坐标确定且 `next_region_id` 严格递增（`:282-303`），用 `Vec<Option<usize>>` 即可 O(1)。
- `region_shapes: HashMap<usize, Vec<[usize;2]>>` —— region_id 即下标，可用 `Vec<Vec<...>>`。
- `frontier: HashMap<usize, HashMap<(usize,usize),usize>>` —— 双层哈希，逐格增删。
- 这些在回溯热路径上每次 insert/remove 都做两次哈希 + 内存分配。量级 KB~MB，但**换扁平数组
  既是内存也是性能优化**（已在 `docs/rust-solver/TODO.md` P1 #3 记录）。

## 5. 🟡 DLX / pieces 候选（次要）

- `Placement { cells: Vec, area, shape: Shape, cell_ids_flat: Vec }`（`pieces.rs:13-19`）
  每个放置四份数据，dedup 时再 `cell_ids_flat.clone().sort()`（`:313`）。
- `DancingLinks.nodes: Vec<DlxNode>`，每个 `DlxNode` 48B（6×usize + count），每格每放置一个。
  量级几 MB，非热点。

## 6. 🟡 `Cell` 结构体 192B（建模层）

`types.rs:88-99` 每个 `Cell` 实测 192B（`docs/重构/data-structures.md`）：`Option<String> symbol`、
`Option<Shape> fence_pattern/shape_pattern` 对多数格子恒 `None` 却常驻；`region_id` 是
aog 求解路径死字段。16×16 盘 256 格 × 192B ≈ 49KB，绝对值不大，但建模臃肿、热路径缓存友好性差。
已在 `docs/rust-solver/TODO.md` P3 #8 记录。
