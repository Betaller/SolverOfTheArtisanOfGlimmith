# 03 · 优化方案

> 分优先级列出方案，每项含机制、改动位置、行为影响（是否可能改变可解性）、工作量与风险。
> 按 `CLAUDE.md` 门禁：**任何影响求解结果的改动**必须同步更新
> `docs/official-puzzles-status.md` + `docs/rust-solver/` 对应篇，并把全量扫描结果
> 存 `results/YYYYMMDD_<sha>.txt` 随提交入库。

---

## 优先级总览

| 优先级 | 方案 | 内存收益 | 行为影响 | 风险 | 工作量 |
|---|---|---|---|---|---|
| **P0** | A1. aog 形状库硬上限 + 提前止损 | 5~7 GB → 数百 MB | 可能改变可解性 | 中 | 小 |
| **P0** | A2. aog 无约束题 upper_bound 合理化 | 同 A1 | 可能改变可解性 | 中 | 小 |
| **P0** | B. rose region_match `visited`/候选预算上限 | 102 MB → 数十 MB | 可能改变可解性 | 低 | 小 |
| **P1** | C. `Pools` 惰性扩容 | 3.6 MB → 按需 | **行为等价** | 低 | 小 |
| **P1** | D. backtrack `HashMap` → 扁平数组 | KB~MB + 提速 | **行为等价** | 低 | 小 |
| **P2** | E. 分配器切换（mimalloc/jemalloc） | RSS 回落更快 | 需实测 | 低 | 小 |
| **P2** | F. 批量模式（子进程复用） | 每进程 5 MB 基线摊销 | 行为等价 | 中 | 中 |
| **P3** | G. 形状库紧凑化 / `Cell` 拆分 | KB~MB | 行为等价 | 高 | 大 |

> 推荐实施顺序：**C → D → B → A**（先白捡后止血；A 因可能改可解性需要最重的回归）。

## A. aog 自由形状搜索止血（P0）

### A1. 形状库硬上限 + 提前止损

**机制**：给 `core.shapes` 加 `MAX_CATALOG_SHAPES`（建议 50k~200k）。当达到上限时：

- `shapes_insert`（`aog/core.rs:168`）直接返回失败，不再累积；
- 或 `place_non_predifined_shape` / `dfs` 在检测到 catalog 超限时返回 -1，提前让出路由
  （pieces → backtrack）。

**改动位置**：`aog/core.rs`（`shapes_insert` / `add_shape_to_shapes`）、`aog/search.rs`
（shape 循环与 `place` 分支）。

**为什么安全**：catalog 达到 20 万唯一形状仍解不出的题，继续枚举第 20 万零 1 个形状找到解
的概率趋近于零；即便真有，路由链的 pieces/backtrack 会接手（只是更慢）。正确性由
`IndependentValidator` 兜底——**错的答案永远不会放行**，只会「这次解不出」。

**行为影响**：改变可解性。必须在官方题库全量回归，统计 DIFF / UNSOLVED 变化（见
`docs/official-puzzles-status.md` §2 的扫描方式）。

### A2. 无约束题的 `upper_bound` 合理化

**机制**：无尺寸约束时 `shape_size_upper_bound = empty_area_cnt`（最大 256，`aog/core.rs:898`）
是爆炸的根。可选收紧策略：

- 参考 C++ `main.cpp` 的实际做法（其 `shape_size_upper_bound` 在无约束时也是区域数，
  行为同样爆炸——但这正是参考缺陷所在，见 [02-根因分析](02-根因分析.md) §1.3）；
- 或对该类题直接跳过 aog（`solver/mod.rs` 路由），交 rose / pieces / backtrack；
  但 `is_rose_capable` 只覆盖 rose 题，watchtower-only 题没有专门求解器，直接跳过会丢解。

**建议**：A1 优先；A2 作为 A1 的补充（catalog 上限到达前的「搜索宽度」本身也不该是 256）。

### A3. deadline 粒度加细（辅助）

`place_non_predifined_shape` 的 4096 步检查点（`search.rs:113`）在 swap 抖动下失效。
可降到 512 步，让 aog 更早、更及时地停住。**不改搜索结果**（deadline 只是停得更准），
风险极低，配合 A1 一起做。

## B. rose region_match 候选预算上限（P0）

### 机制

1. **`visited` 加硬上限**（`region_match.rs:40`）：当 `visited.len()` 超过阈值（如 50 万）
   提前结束该 seed 的 BFS。`CANDIDATE_CAP` 只挡 results，挡不住中间状态，必须挡 visited。
2. **消除克隆层**：
   - `candidates_by_size`（`:412`）的 `c.clone()` 可改为存引用（生命周期允许时）或
     只存 `CellSet` 的所有权转移（`all_candidates` 构建时即分桶，避免二份拷贝）；
   - `match_regions_mrv` 的 `sized.push(list.clone())`（`:448`）改为按引用借用；
3. **总候选预算**：所有 seed 候选数总和设上限（如 30 万），超限放弃 region_match 转 rose_growth
   或直接失败。

### 行为影响

改变可解性（C4-2 这类题超限后交给 rose_growth / 失败）。但 rose_growth 本就是兜底路径，
且 C4-2 现在也解不出——**内存预算换确定性，不损失已解题目**。需官方题库 rose 题回归。

## C. `Pools` 惰性扩容（P1，白捡）

### 机制

`Pools::new`（`aog/types.rs:297`）改为只分配 `Vec` 骨架，`place_non_predifined_shape` /
`dfs` 在 `index` 超过 `pools.place.len()` 时按需 `push`（倍增扩容）。`mark_skip` / `mark_size`
同理（它们已在 `dfs` 里按需 `resize`，只是 `place` 层全量预分配了）。

### 行为等价性

`pools.place[index]` 只按 index 访问，惰性扩容不改变任何取值。**纯内存优化，不改搜索语义**，
风险最低，建议最先落地。预期小盘 RSS 5.6 MB → ~2 MB。

## D. backtrack 扁平化（P1，白捡）

### 机制

`BacktrackState`（`backtrack.rs:55-70`）扁平化：

| 现状 | 改为 | 依据 |
|---|---|---|
| `cell_to_region: HashMap<(usize,usize),usize>` | `Vec<Option<usize>>`（H×W 扁平） | 坐标确定、下标 O(1) |
| `region_shapes: HashMap<usize, Vec<[usize;2]>>` | `Vec<Vec<[usize;2]>>` | `next_region_id` 严格递增、回溯 pop |
| `region_clue: HashMap<usize,usize>` | `Vec<Option<usize>>` | 同上 |
| `frontier: HashMap<usize, HashMap<(usize,usize),usize>>` | `Vec<HashMap<usize,usize>>` 或计数数组 | 双层哈希 → 单层 |

同时 `regions_respect_boundaries`（`solver/mod.rs:124-166`）的
`HashMap<(usize,usize),usize>` 也改 `Vec<Option<usize>>`。

### 行为等价性

只换存储，逻辑逐行等价。已在 `docs/rust-solver/TODO.md` P1 #3/#4 记录。

## E. 分配器切换（P2）

### 机制

Rust 默认 system `malloc`。aog 大量 transient `Vec` churn 后 RSS 不回降（arena 效应，见
[04-内存泄露审计](04-内存泄露审计.md) §3.2）。测 `mimalloc` / `jemalloc`：
`cargo add mimalloc`，`global_allocator = MiMalloc`。逐场景对比 RSS 峰值与回落。

### 注意

- 分配器本身不解决「形状库无界增长」这一根因，只改善峰值/回落。
- 引入第三方依赖，需评估发布体积与平台兼容（Windows 上 mimalloc 支持良好）。

## F. 批量模式（P2）

### 机制

Python `RustSolver` 每题 spawn 一次 rsolver（`src/solver/rust_solver.py`），每次启动摊销
~5 MB 进程基线 + `Pools` 3.6 MB。改为一次进程循环处理多题（stdin 逐行 JSON / 逐题求解）。

### 行为影响

改子进程协议 + Python 调用方，需兼容单题模式。已在 `docs/rust-solver/TODO.md` P2 #7 记录。

---

## G. 形状库紧凑化 / `Cell` 拆分（P3，大改）

- `Shape.nodes: Vec<Node>`（`aog/types.rs:75-80`）每形状两次堆分配，可改 `Arc<[Node]>` 或
  按尺寸分桶的定长小数组（aog 内部已用 `[Node; MAX_SHAPE_SIZE]` 定长数组，catalog 侧未用）。
- `Cell` 192B → 「线索模型 / 求解状态」分离（见 `docs/重构/data-structures.md`）。

两者风险高、收益相对小，排在最后；`Cell` 拆分已在 `docs/rust-solver/TODO.md` P3 #8。
