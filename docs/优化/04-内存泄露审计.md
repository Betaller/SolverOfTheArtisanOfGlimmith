# 04 · 内存泄露审计

> 回答两个问题：1) `rsolver` 有没有经典意义上的 Rust 内存泄露？ 2) 实测的「RSS 不回落」
> 是怎么回事？本文件把「泄露」与「不释放」区分清楚，避免优化时修错方向。

---

## 1. 结论先行

| 问题 | 结论 |
|---|---|
| Rust 所有权语义下的经典泄露（`Rc` 循环 / `Box::leak` / `ManuallyDrop`） | **没有** |
| 结构化的长期驻留（搜索期不断累积、进程结束前不释放） | **有**：aog 形状库 |
| 分配器效应（transient 分配后 RSS 不回降） | **有**：system `malloc` arena |
| 单项可修的「忘了释放」 | 基本没有（有一处 `slash_dist_buf` 不缩容，可忽略） |

**一句话**：`rsolver` 的内存问题是「**该停不停的增长**」和「**释放了但没还给操作系统**」，
不是「指向悬空内存」的泄露。所以优化方向是**加预算/上限**（[03-优化方案](03-优化方案.md) A/B），
而不是找 `free` 遗漏。

---

## 2. Rust 语义泄露审计

### 2.1 审计面

- **`Rc` / `Arc` 循环引用**：全仓无 `Rc`/`Arc` 使用（`rsolver/src/**` 仅用到 `RefCell`，
  而 `RefCell` 不参与所有权/生命周期，无循环引用风险）。`RefCell` 用于 `Pools` 层的并行借用
  （`aog/types.rs:292-295`），借用都在同一 `solve_aog` 栈内成对出现，`borrow_mut` 的 guard
  在作用域结束释放，**无借用泄漏**。
- **`Box::leak` / `mem::forget` / `ManuallyDrop`**：源码中不存在。
- **全局 static 累积**：无 `static mut` 或 `lazy_static` 累积结构。
- **`main()` 一次性分配**：`PuzzleJson` / `Puzzle` / `Solution` 随 `main` 退出释放，无驻留。

### 2.2 唯一的「增长型驻留」

`AoGCore`（`aog/core.rs:12-37`）的三张结构在整个求解期间单调增长、**进程结束才释放**：

```text
core.shapes: Vec<Shape>                       ── 自由形状搜索不断插入
core.node_to_shape_index: HashMap<…, Vec<_>>  ── 每个插入对每个节点 push
core.shape_digest_index: HashMap<u32, Vec<_>> ── 每个唯一 digest 一条
```

这些不是「忘记释放」，而是「搜索自身没有收敛、插入没有上限」。它们常驻的时间 = 进程存活时间。
这就是实测 RSS 平台在 6.8 GB 不回落的原因（[01-内存现状与实测基线](01-内存现状与实测基线.md) §2）。

> 修复方式不是「在析构里释放」（Rust 会自动释放），而是**阻止它无限增长**（方案 A1）。

## 3. 「释放了但没还给 OS」——分配器效应

### 3.1 现象

aog 搜索期间大量 `Vec`/`HashMap` 分配与释放（`shape_buf`、候选 `Vec`、`dfs_ctx.block_adj`
每次清空重建等）。Rust 默认全局分配器是系统 `malloc`；`free()` 后的块通常留在 malloc 的
**bin / arena 缓存**里复用，**不会立刻还给操作系统**（`munmap`）。于是：

- RSS 反映的是「malloc 持有的高水位」，而非「当前存活对象」；
- 搜索结束后即使对象都释放了，RSS 也可能长期停留在高位；
- 大量不同大小的分配会使堆**碎片化**，加剧不回降。

### 3.2 为什么优化它

分配器效应本身不是 bug，但在**单进程多题批量模式**（方案 F）下会被放大：每题积累的高水位
无法复用给下一题，峰值被持续撑高。缓解手段：

- 换 `mimalloc`/`jemalloc`（方案 E）：激进返回、低碎片；
- 或接受现状，仅保证单题峰值受控（方案 A/B 把高水位本身压下去）。

### 3.3 一处小瑕疵（可顺手修）

`PlaceLevel.slash_dist_buf`（`aog/types.rs:253`）用 `resize` 只增不减，搜索结束后保留最大尺寸；
最大 `MAX_SHAPE_SIZE × (types+1) × (ref_len+1)`，量级小（几十 KB），但符合「该缩不缩」，
可加 `shrink_to_fit` 或在 `dfs` 层退出时清空。

## 4. 排查工具建议

| 工具 | 用途 | 当前可用性 |
|---|---|---|
| `valgrind --leak-check=full` | 确认「真正漏掉没释放」的内存 | 未安装（本机），可 `apt install valgrind` |
| `/usr/bin/time -v` 峰值 RSS | 快速基线 | ✅ |
| `/proc/<pid>/status` VmRSS / VmPeak 采样 | 时域增长曲线 | ✅ |
| `perf record`（需 `perf_event_paranoid<3`） | 分配热点采样 | 本机 paranoid=4，需 sudo/调低 |
| `jemalloc --enable-prof` / `malloc_count` | 分配计数、按调用点归因 | 需引入依赖 |
| `LD_PRELOAD` + `mallinfo2` | malloc arena 状态 | 可用 |

> 对 rsolver 而言，`valgrind` 的 leak-check 预期**零输出**（确认无经典泄露）；真正要盯的是
> VmRSS 时域曲线的**斜率**与**高水位**，而不是 leak report。

## 5. 与「内存泄露」相关的常见误解

1. **「RSS 涨了 = 泄露」**：不对。RSS 涨可能只是 malloc 高水位 / 结构化驻留。判断泄露要看
   「对象不再可达却仍占用」——rsolver 没有。
2. **「Rust 内存安全所以不会泄露」**：不全对。Rust 防的是**悬垂/use-after-free**，
   不防**无界增长**（Vec 一直 push）和**分配器不归还**。本项目的两类问题正是后两者。
3. **「优化内存要改 C++ 移植语义」**：形状库无界是参考缺陷，加预算/上限是**修复**而非背离，
   且路由链 + 独立验证器保证正确性。
