# 23 — 求解器返回信息完善方案

> 状态：**已落地**（2026-08-17，P0+P1 合并实施）。
> 目标：让求解结果能回答「一共跑了哪些求解器、各自耗时多少、各自为何失败、
> 总体耗时多少、最终是否求解、由哪个求解器解出」六个问题。
> 关联源码：`rsolver/src/solver/mod.rs`（分派）、`rsolver/src/types.rs`（Solution）、
> `rsolver/src/io.rs`（JSON 序列化）、`src/solver/base.py`（路由）、
> `src/solver/rust_solver.py`（子进程封装）、`src/models/solution.py`（领域模型）、
> `src/ui/main_window.py`（UI）、`scripts/benchmark_rust_solver.py`（基准）。
>
> 更新日期：2026-08-17

---

## 0. 一句话结论

求解器的「多求解器」实际发生在 **Rust 子进程内部**（aog → rose → edge_csp → pieces →
backtrack 五段串联），而当前 JSON 只透出**最终获胜模块名 + 总耗时**，中间每个模块的
耗时、失败原因（超时 vs 无解 vs 校验失败）全部被 `Option<Vec<RegionInfo>>` 的 `None`
吞掉。方案：在 Rust `Solution` 上新增 `attempts: Vec<SolverAttempt>` 逐模块记录
`{solver, status, elapsed_ms, note}`，贯穿 JSON → Python `Solution.attempts` →
路由/UI/benchmark 三层呈现，向后兼容（新增可选字段）。

## 1. 现状盘点

### 1.1 已透出的信息（够用项）

| 需求 | 现状 | 位置 |
|---|---|---|
| 最终是否求解 | ✅ `Solution.solved` | `types.rs` / `solution.py` |
| 成功求解的求解器 | ✅ `Solution.solver`（aog/rose/edge_csp/pieces/backtrack 之一） | `types.rs:170` |
| 总体耗时 | ✅ `Solution.elapsed_ms`（自 `solver::solve` 起点计时） | `types.rs:163` |
| 失败时的一条原因 | ⚠️ 只有**最终** `error_message`（"No solution found" / "fails rule validation"） | `mod.rs:147-155` |

### 1.2 缺口（本次要补的）

| 需求 | 现状 | 根因 |
|---|---|---|
| 一共使用了哪些求解器 | ❌ 只知最终获胜者；aog 超时后 pieces 解出时，只见 "pieces" | 中间模块无记录 |
| 各求解器耗时分别多少 | ❌ 只有总 `elapsed_ms`，无 per-module 分解 | 未在分派处计时 |
| 各求解器失败原因分别是什么 | ❌ 每个模块 `None` 时"超时 / 无解 / 校验失败"三者不可分 | 返回类型 `Option<Vec<RegionInfo>>` 把三类失败压成同一个 `None` |

关键代码：`mod.rs` 分派处（`solve_aog`/`solve_rose`/`solve_edge_csp`/`solve_pieces`/
`solve_backtrack` 五处 `if let Some(regions) = ... { return build_solution(...) }`），
失败时全部 `fallthrough`，不落任何日志到结果里（仅 aog/pieces/backtrack 有 `eprintln!`
debug，且需 `AOG_DEBUG` 环境变量）。

## 2. 失败原因分类（核心定义）

每个模块一次尝试的终态归入下列之一。这是"失败原因"字段的取值域，也是各模块
`Option` 返回值需要改造成枚举的直接动力：

| status | 含义 | 触发示例 |
|---|---|---|
| `success` | 找到并通过 `validate::validate` 的解 | `Some(regions)` 且 `build_solution` 校验通过 |
| `timeout` | 用满预算仍未搜完（deadline 命中） | aog `dfs` 热循环到 `deadline` 返回 -1 |
| `exhausted` | 预算内搜完、确认无解 | 搜索空间耗尽，`None` 且未到 deadline |
| `validation_failed` | 找到候选解但 `validate::validate` 拒绝 | `build_solution` 里校验失败的路径 |
| `not_attempted` | 未尝试（不适用 / 被前置求解器抢先） | 无 shape_pool → pieces 跳过；aog 已解 → 后续全跳过 |
| `error` | 异常 / panic / JSON 损坏（子进程层） | `returncode != 0`、`JSONDecodeError` |

> 注意：`validation_failed` 目前有两个落点——aog/edge_csp 在**模块内部** `validate`
> 失败后返回 `None`（与 exhausted 不可分）；pieces/rose/backtrack 走 `build_solution`
> 统一校验，失败时返回 `Solution { solved:false, error_message:"...fails rule
> validation" }`（已可区分）。方案要把这两处统一成 `validation_failed`。

## 3. 方案设计

### 3.1 Rust 数据结构（`types.rs`）

```rust
#[derive(Debug, Clone, Serialize)]
#[serde(rename_all = "snake_case")]
pub enum SolverStatus {
    Success,
    Timeout,
    Exhausted,
    ValidationFailed,
    NotAttempted,
    Error,
}

#[derive(Debug, Clone, Serialize)]
pub struct SolverAttempt {
    pub solver: String,        // "aog" | "rose" | "edge_csp" | "pieces" | "backtrack"
    pub status: SolverStatus,
    pub elapsed_ms: u64,       // 本模块自身的 wall-clock（自进入该模块到返回）
    pub note: Option<String>,  // 可选细节：校验错误摘要 / "not applicable (no rose_window)"
}

pub struct Solution {
    // ...现有字段不变...
    pub attempts: Vec<SolverAttempt>,   // 新增，默认空
}
```

### 3.2 分派处采集（`solver/mod.rs`）

在 `solve` 中引入一个采集闭包/辅助函数，把五处调用统一包裹：

```rust
fn record(
    attempts: &mut Vec<SolverAttempt>, solver: &str,
    start: &Instant, deadline: Option<Instant>,
    outcome: ModuleOutcome,
) {
    let status = match outcome {
        ModuleOutcome::Solved(_) => SolverStatus::Success,
        ModuleOutcome::ValidationFailed => SolverStatus::ValidationFailed,
        ModuleOutcome::None => match deadline {
            Some(d) if Instant::now() >= d => SolverStatus::Timeout,
            _ => SolverStatus::Exhausted,
        },
    };
    attempts.push(SolverAttempt {
        solver: solver.into(),
        status,
        elapsed_ms: start.elapsed().as_millis() as u64,
        note: None,
    });
}
```

其中 `ModuleOutcome` 是新增的模块返回值枚举（见 3.3），替换各模块的
`Option<Vec<RegionInfo>>`。**超时 vs 无解**的判定用 `Instant::now() >= deadline`
作第一层近似（模块内部已有 deadline，且 search.rs Fix B/C 保证 deadline 前停止）；
若要精确，需各模块把"是否命中 deadline"的布尔值随结果带出（见 3.4）。

分派处改造后（以 aog 为例，其余四处同构）：

```rust
if let ModuleOutcome::Solved(regions) =
    aog::solve_aog(puzzle, deadline) {
    attempts.push(SolverAttempt { solver:"aog", status: Success, .. });
    return build_solution_trusted(regions, &start, puzzle, attempts);
}
attempts.push(/* aog: timeout|exhausted, elapsed */);
// fallthrough → rose / edge_csp / pieces / backtrack 依次记录
```

各模块的 `is_*_capable` 判定不通过时，也应 push 一条 `not_attempted`（带 note），
使"一共用了哪些"的清单完整可读。

### 3.3 模块返回签名改造

把五个 `solve_*` 的 `Option<Vec<RegionInfo>>` 换成 `ModuleOutcome`：

```rust
pub enum ModuleOutcome {
    Solved(Vec<RegionInfo>),
    ValidationFailed,   // 找到候选但 validate 拒绝
    None,               // 无解（超时与否由 wrapper 依据 deadline 判定）
}
```

| 模块 | 位置 | 现有 `None` 语义 | 改造点 |
|---|---|---|---|
| aog | `aog/mod.rs:20` | `dfs` 返回 -1（超时/无解不分）；内部 validate 失败也返回 `None` | 内部 validate 失败 → `ValidationFailed`；`dfs==-1` → `None`（wrapper 判超时） |
| rose | `rose/mod.rs:86` | 无 symbol / m==0 / region_match+grow 均未解 | 三处 `None` 改 `ModuleOutcome::None` |
| edge_csp | `edge_csp/mod.rs:476` | `solver.solve()?` 无解；内部 validate 失败也 `None` | 内部 validate 失败 → `ValidationFailed` |
| pieces | `pieces.rs:37` | DLX 无解 | `ModuleOutcome::None` |
| backtrack | `backtrack.rs:10` | 无解 | `ModuleOutcome::None` |

> aog 与 edge_csp 的「内部 validate 失败」是当前被 `None` 掩盖的信息——它们本可以
> 归入 `ValidationFailed`（说明"模型偏松、搜出了假解"），对 FAIL 根因分析价值最高。

### 3.4 超时精确化的可选升级

`3.2` 用 deadline 近似判定 timeout/exhausted，有一处盲区：模块若恰在 deadline 附近
因"自然耗尽"返回，会被误判为 timeout。精确化两条路（择一，Phase 2 再做）：

1. **模块带出 flag**：aog 的 `search::dfs` 在热循环命中 deadline 时置一个
   `&mut bool deadline_hit`，随结果返回；pieces/backtrack 同理。改动深入搜索核心。
2. **共享 Deadline 类型**：`clock.rs` 已有 `Instant`，扩展一个 `Deadline { hit: Cell<bool> }`
   贯穿各模块，命中即置位。与 memory 中「deadline 盲区」整改（[[hang-root-cause-deadline-blindspots]]）
   天然衔接。

Phase 1 用近似值即可满足"各求解器耗时/失败原因"的可观测需求，精确 flag 留待与
deadline 盲区整改合并处理。

### 3.5 JSON 协议（`io.rs`）

`SolutionJson` 与 `solution_to_json` 增加 `attempts` 数组（`#[serde(skip_serializing_if
= "Vec::is_empty")]` 可选，保证旧消费者不受影响）：

```json
{
  "solved": true,
  "elapsed_ms": 1234,
  "solver": "pieces",
  "attempts": [
    {"solver":"aog","status":"timeout","elapsed_ms":3000,"note":null},
    {"solver":"rose","status":"not_attempted","elapsed_ms":0,"note":"no rose_window"},
    {"solver":"edge_csp","status":"not_attempted","elapsed_ms":0,"note":null},
    {"solver":"pieces","status":"success","elapsed_ms":1234,"note":null}
  ]
}
```

### 3.6 Python 侧

**`src/models/solution.py`** —— 复用/扩展一个统一 `SolverAttempt`：

```python
class AttemptStatus(StrEnum):
    SUCCESS = "success"
    TIMEOUT = "timeout"
    EXHAUSTED = "exhausted"
    VALIDATION_FAILED = "validation_failed"
    NOT_ATTEMPTED = "not_attempted"
    ERROR = "error"

@dataclass(slots=True)
class SolverAttempt:
    solver: str
    status: AttemptStatus
    elapsed_ms: int
    note: str | None = None

@dataclass(slots=True)
class Solution:
    # ...现有字段...
    attempts: list[SolverAttempt] = field(default_factory=list)
```

**`src/solver/rust_solver.py`** —— `_parse_solution` 读取 `data.get("attempts", [])`
反序列化为 `list[SolverAttempt]`。`solver` 字段保留（向后兼容），成功者可从
`attempts` 里 `status==success` 的最后一条等价推导。

**`src/solver/base.py`** —— 两层 attempt 的关系（重要，避免混淆）：

- **L1（wrapper 层）**：`SolverRouter._attempts`，记录 Python 求解器链（当前仅
  `RustSolver`）的每次尝试。已存在，字段是 `{solver_name, solved, elapsed_ms, steps,
  error}`。
- **L2（module 层）**：新增 `Solution.attempts`，记录 Rust 内部五模块。

建议：把 `base.py` 的 `SolverAttempt` 统一为上面的 `status` 枚举版本（`solved` →
`SUCCESS/…`、`error` → `note`），两级共用同一个 dataclass；`route()` 成功返回前把
`sol.attempts`（L2）合并进返回对象，`router.attempts`（L1）保持独立可查。

**`src/ui/main_window.py`** —— 结果面板加一张小表：`求解器 | 状态 | 耗时 | 原因`，
从 `solution.attempts` 渲染（当前 625-641 行只显示总耗时 + 单条 error）。

**`scripts/benchmark_rust_solver.py`** —— `PuzzleResult` 增 `attempts` 字段，JSONL
落盘；FAIL 行的 `via={solver}` 改为带完整 attempt 链（如 `aog:timeout→pieces:success`），
直接服务 FAIL 根因分类（[[fail-hardness-ceiling]]）。

## 6. 风险与边界

- **行为等价性**：P0 是纯观测层（计时 + 记录 + 序列化），不改任何搜索语义，正确性
  由独立验证器兜底不变。P1 把 `None` 换成 `ModuleOutcome::None`，若落点替换有遗漏
  会导致某模块"提前返回"或"误报状态"，必须 `cargo test` + 全量 benchmark 回归确认
  PASS 数、DIFF 数不变。
- **计时口径**：各模块 `elapsed_ms` 是**本模块自身 wall-clock**，不含被前置模块占用的
  时间；总 `elapsed_ms` 仍是全局起点。文档需写明两者关系，避免"各模块耗时之和不等于
  总耗时"的困惑（模块间有 `is_*_capable` 判定、`build_solution` 校验等非模块时间）。
- **deadline 近似误判**：P1 用 `Instant::now() >= deadline` 分 timeout/exhausted，在
  "恰好耗尽于 deadline 附近"时可能误判，属已知精度上限，P2 消除。
- **向后兼容**：`attempts` 为新增可选字段，旧消费者（旧 benchmark、手工 `curl`/脚本）
  不解析即忽略，不影响。

## 8. 实施记录（2026-08-17 落地）

P0+P1 合并实施（一次改到位，避免改两次）。三个待确认项的拍板：

1. **两层合并**：✅ 统一。`SolverAttempt` 移到 `src/models/solution.py`，L1（`SolverRouter
   ._attempts`）与 L2（`Solution.attempts`）共用，带 `status: AttemptStatus` 枚举 + 兼容

### 8.3 已知边界

- **OOM / 外部 kill 时 `attempts` 为空**：进程被 OOM-killer 或 wall-budget 超时 kill 时没机会
  写 JSON，`_parse_solution` 拿到空/残缺输出，`attempts=[]`。这是预期——这类题的根因是
  OOM/挂死（doc 18），不在 attempts 可观测范围内。
- **超时近似误判**：`record_module_with_elapsed` 用 `Instant::now() >= deadline` 分
  timeout/exhausted，模块恰好耗尽于 deadline 附近可能误判 timeout。留待 deadline 盲区整改。
- **P2/P3 未做**：超时精确化（`Deadline { hit }` 贯穿搜索核心）与 UI/benchmark 深化呈现
  留待后续——本次 P0+P1 已满足六个需求。
