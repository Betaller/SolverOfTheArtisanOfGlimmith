## 0. 一句话结论

当前 Rust 求解器（`aog→rose→edge_csp→pieces→backtrack` 串行链）已是「手写 DFS + 激进领域剪枝」范式下的**业界最优组合**，天花板约 **1120–1160 / 2488**（见 `21`）。**前 23 篇几乎穷尽了「单线程算法」这一维度**；剩余可榨出的大头集中在三个被忽略的维度：

1. ⭐ **并行化**——五个求解模块当前**串行**且各自独吞完整 `timeout_ms`，但彼此**完全独立、无共享可变状态**。改成「并发跑、先赢者取消其余」即可在**零算法改动**下把墙钟预算利用率从 `1/5` 提到接近 `1`，对大量「单一模块差点解出」的题是直接净增解出。
2. ⭐ **机器学习 / 学习启发式**——2488 道官方题是可免费利用的**监督信号源**，可学「变量序 / 值序 / 何时切模块」等策略，前 23 篇零涉及。
3. ⭐ **底层系统调优 + 实验方法论**——消除 backtrack 热路径的 `HashSet` 分配、去掉双重 `validate`、统一基准纪律（当前 `RUST_PARTS=4` 把墙钟放大 4× 误导了所有「单题耗时」读数）。

> 本文新贡献 = §4（并行化）、§5（ML 启发式）、§6（系统调优）、§7（实验方法论）、**§11（15 条进一步全新方向）**、§8（速赢）。其余方向均已在 `docs/优化/` 前 23 篇成体系，本文只做**索引 + 状态矩阵 + 补充批判**，不重复正文。

## 2. 现状速览（写于本文时）

- **架构**：Python `RustSolver` 仅做 JSON 序列化 + 子进程调用 + 独立验证；热路径 100% 在 `rsolver/`（Rust）。
  - 路由链 `solver/mod.rs:16`：**串行** `aog`(预算 3s if rose-capable 否则 full) → `rose` → `edge_csp` → `pieces`(DLX) → `backtrack`(最终回退)。
  - 每个模块拿到**完整** `timeout_ms` 作为自己的 deadline（`mod.rs:53-56`），但因为串行，墙钟最坏 = 5×timeout（实际 4 个有能力模块）。
- **真实热路径**：`backtrack` 在官方语料几乎从不触发（aog/rose/edge_csp 先赢，见 `11` §1.2）。所以「优化 backtrack 单节点」收益远低于「优化 aog / edge_csp 传播强度」与「让强模块更早赢」。
- **pieces (DLX)**：仅 4 道全铺满题能从精确覆盖获益，其余 167 道白费候选生成（`10` §3.2）。未来应删除或改为「部分覆盖 + 移交」。
- **当前成绩基线（2026-08-29 实测，见文末附录）**：全量 `--timeout 15 -j 8` → **1066 / 2488 PASS，192 FAIL，0 DIFF**。（`21` 估计的 1120–1160 是 40s 超时口径；15s 口径下 1066 与之自洽。）
- **失败画像**（引 `21`）：~117 无解（剪枝/范式不足）+ ~45 超时 + 19 OOM（配置 bug）。单规则 FAIL 极少，绝大多数是 2–4 规则组合，瓶颈常是「某规则缺传播/范式错配」。

## 4. ⭐ 并行化深度分析（本文核心补遗）

> 前 23 篇只在 `11` §4.5C 提了一句「谜题内并行少见」。**这是被系统性低估的整个维度**。下面分三层。

### 4.1 模块间并发「先赢者取消」（ROI 最高，0 算法改动）

**现状**：`solver/mod.rs:16` 五个模块**串行**执行，每个拿完整 `timeout_ms`。即一道题最坏墙钟 = 4~5×timeout（且 Python 侧 `_wall_budget` 再 ×4，`RUST_PARTS=4`，见 §7.1）。

**⚠️ 实测校准（2026-08-29 全量基准，445 PASS 快照）**：439 道由 `aog` 首解，仅 **6 道**由后续模块解出（全为 `aog:timeout→rose:success`，前序浪费墙钟合计 18s）。结论：**串行浪费主要体现在墙钟，而非「后续模块拿不到预算」——因为每个模块独立拿到完整 `timeout_ms` deadline，串行失败时后续模块仍跑满自己的 timeout**。因此：

- 并发**不会**神奇提升「超时类」题的解出率（每模块本就跑满 timeout）。
- 并发的**真实收益有两点**：
  1. **OOM/崩溃隔离（直接增解）**：aog 自由形状库 OOM（`exit -9`，档① 19 道）当前会**杀掉整个子进程**，导致 rose/edge_csp/pieces/backtrack 全部没机会跑 → 题 FAIL。若每模块在独立线程/进程，aog OOM 只取消自己，edge_csp 仍能解出（round 18 指出这 5 道 `0977/0631/1110/0491/1395b` 可被 edge_csp 接住）。**这是并发唯一确定的「净增解出」来源。**
  2. **墙钟效率 / UX**：不必串行等一个必败的 aog 跑满 timeout；先赢者取消其余，单题墙钟从 4~5×timeout 降到「最快模块的实际耗时」。批量吞吐与 UI 实时求解直接受益。

**方案**：用 OS 线程（或独立子进程）**并发**跑有能力的模块，共享「已解出」标志；任一模块返回 `Solved` 即让其余模块在下一个 deadline 检查点**协作取消**（deadline 检查已存在：`aog/search.rs:858`、`backtrack.rs:470`、`edge_csp/mod.rs:458`、`dlx.rs:192`）。first-wins barrier。OOM 隔离建议用**独立子进程**（每模块一个），最稳。

- **收益**：(1) 接住档① OOM 题中 edge_csp-capable 的 5 道（直接净增解出）；(2) 墙钟效率 4~5× → ~1×。完全不改搜索语义、零回归风险（正确性仍由独立验证器兜底）。
- **风险**：低（隔离用子进程时几乎为零；用线程需保证撤销栈线程局部）。
- **工作量**：小–中（~150–300 行 + 共享时钟/取消原语；子进程方案略多）。
- **落地位置**：`solver/mod.rs:16` 重写为并行分发；新增 `solver/race.rs`（线程）或 `race_proc.rs`（子进程）。

### 4.2 模块内并行 DFS（work-stealing）

**现状**：每个模块内部是单线程 DFS。

**方案**：
- aog `place_non_predifined_shape` 的 slash-distance 元组枚举（`search.rs:647-708`）、rose 的 per-seed 候选 BFS（`region_match.rs:53`）、pieces 的 `generate_all_placements`（`pieces.rs:207`）——这些**枚举/生成**阶段天然可并行（无依赖）。可用 rayon 分块。
- 搜索树本身并行需「作业窃取 + 可中断」：把 DFS 节点压入工作队列，N 线程各取一个子树深搜；某个线程找到解即全局取消。挑战：撤销栈（backtrack 的 push/pop、`edge_csp` 的 `changed` trail）需线程局部或改为「路径拷贝 + 比较」。

**收益**：大网格（档 ⑤ 根本难）可在多核上线性加速，直接对抗 40s 超时档。
**风险**：中。撤销状态线程安全 + 确定性丢失（回归比对需 `--retry-timeouts` 单独确认）。
**工作量**：中–大（~500 行 + rayon 依赖）。
**注意**：确定性对官方解比对（DIFF 检测）无关（解唯一），仅影响「哪条路径先找到」，可接受。

### 4.3 谜题间并行 + 子进程复用

**现状**：benchmark 已用 `-j 8` + `--batch N`（`P2 #7` 已落地，~6× 吞吐）。
**补强**：单题调用（UI `solver_runner`）也可常驻一个 batch 子进程复用，消除 spawn 开销（`rust_solver._find_binary` 每次新建进程）。UI 实时求解体验直接受益。

### 4.4 GPU offload（远景，谨慎）

连通性 flood-fill / 形状库匹配是「多独立小任务」形态，理论上可 GPU 批处理。但：①当前瓶颈是搜索树（强依赖、难并行），非规整矩阵；②Rust→GPU 需重写核心，得不偿失。**结论：不推荐**，标记 ⚪。SAT/ILP 后端（若未来做 §5.3 混合）的 propagate 阶段才有 GPU 价值。

## 5. ⭐ 机器学习 / 学习启发式（本文核心补遗，前 23 篇零涉及）

> 2488 道官方题 + 每题的 per-module attempts 追踪（`23` 已落地）构成**免费监督数据集**：我们知道每题「被谁解出、各模块耗时、失败原因」。这是学策略的金矿。

### 5.1 学「模块选择 / 路由」策略（最易落地）

**思路**：用题面特征（网格尺寸、各规则有无、线索密度、area/compass 约束强度、pre-boundary 数量…）训练一个轻量分类器（决策树 / 小 MLP / 甚至查表），预测「哪条模块链最可能先赢」。当前 `mod.rs` 的 capability 判断（`is_rose_capable`/`is_edge_csp_capable`，`mod.rs:373-381`）是**手写硬规则**，可让模型替我们排序甚至裁剪模块。

- **数据**：`results/bench/*.jsonl` 的 `attempts` 字段（已记录每题各模块 status/elapsed）。
- **收益**：减少「串行跑满 5 个模块」的无效墙钟；配合 §4.1 并发，模型可给模块排优先级（先跑高置信模块）。
- **风险**：极低（纯调度层，不影响正确性）。**建议先做。**

### 5.2 学「变量序 / 值序」启发式

**思路**：标准 SAT/CP 成功做法（VSIDS、冒泡排序学习）的变体。对 aog/backtrack 的「选哪格 / 选哪个形状 / 选哪个邻居区域」分支点，用历史求解轨迹学一个打分函数（特征：frontier 大小、area 剩余、是否 clue 格、相邻区域形状多样性…）。

- **数据**：在求解过程中采样（state_features → chosen_branch → 是否导致回溯），训练策略网络或梯度提升树。
- **收益**：可能把 §3.1 的手写 MRV 链路提升到「问题自适应」级别，对档 ③/⑤ 硬题有突破潜力。
- **风险**：中（需插桩采集轨迹、防过拟合到训练分布）。**工作量**：中。

### 5.3 轻量「冲突学习 / nogood」

**思路**：CDCL 的核心优势是学冲突子句（`11` §2.3 已点出 DLX 无学习是短板）。可在一个模块内维护「冲突特征 → 禁止」的轻量 nogood 表（per-rule-type 的冲突簇），类似 `11` §4.3 的 *conflict-driven shape skipping*（参考 AoG_Solver，⭐⭐）。ML 角度：用历史冲突训练「哪些形状/边赋值组合易冲突」，预存为 nogood。

- **收益**：把「无学习手写 DFS」部分补上 SAT 的学习能力——`11` 已论证这是极硬实例上超越手写 DFS 的关键。
- **风险**：中（nogood 库膨胀需 cap + LRU）。

### 5.4 随机化重启（cube-and-conquer 风格）

**思路**：对单模块搜索，周期性随机重置根（保留学到的 nogood / 形状跳过的反向索引），换一个变量序再搜。对「单一模块差一点」的超时题，重启常能撞到更短路。成本极低（加一个随机 seed 源 + 重启计数器 + deadline 切片）。**这是 ML/学习之外的「无模型」探索杠杆，前 23 篇未覆盖。**

## 6. ⭐ 底层系统调优 / 代码生成（本文补遗）

> 前 23 篇提过 env 缓存、region_of O(n²)→O(1)、HashMap→Vec（已落地）。下面补**仍未被覆盖**的低层点。

### 6.1 消除 backtrack 热路径堆分配（高 ROI）

`backtrack.rs` 热路径仍有两处 per-node 分配（`11`/`15` 已部分改但没改净）：
- `dfs`（`backtrack.rs:519-549`）每节点建 `rid_set: HashSet<usize>` + `valid_rids: Vec<usize>`。
- `cell_domain_size`（`backtrack.rs:912`）**每次调用新建 `HashSet`**；`pick_next_cell`（`backtrack.rs:1012`）对**每个**未决格调用它 → 16×16 盘每树层 ~256 次 HashSet 分配。

**改法**：域 = 相邻区域 id 集合，可用「固定小数组（≤4 邻居）+ 计数」或 `u64` 位图（region id < 64）替代 HashSet；`cell_domain_size` 改纯计数循环。预期把 backtrack 单节点成本降一个数量级——**虽然 backtrack 当前不触发，但它是「模块并发后」可能的 winner，且未来接手大网格时直接受益**。

### 6.2 区域表示 SIMD / 位向量

`cell_to_region` 是 `Vec<Option<usize>>`（usize = 8B）。连通性检查（flood-fill、边界判定）频繁整盘扫描。可：
- 用 `u32`/`u16` region id（区域数 ≤ 256，u8 都够）→ 内存减半，cache 命中率↑。
- 边界状态用 `u64` 位向量（每 bit = 一条边 cut/uncut），配合 `popcount`/`ctz` 做顶点度检查，替代 `edge_csp` 的 `Vec<EdgeState>` + 逐边分支。
- aog 的 `u32` bitfield 网格已是最佳实践，可把 `validate::validate` 的 `is_connected`（`validate.rs:393` 每区域 `HashSet`）改 DSU 或位向量。

### 6.3 去掉双重 validate

`pieces.rs:667` 在 `reconstruct_and_validate` 里调一次 `validate`，`mod.rs:304` 的 `build_solution` 又调一次（`11`/`15` 已记录）。**对每道被 pieces 解出的题，22 条规则全量扫描跑两遍**。改法：`build_solution_trusted`（aog 已用）扩到 pieces/rose/backtrack——模块内部已自验，出口只做「边界一致性快速复查」而非全量 22 规则。预期节省一道题 ~1 次完整验证的 CPU（对秒级题显著）。

### 6.4 分配器 / 编译

- 链接 `jemalloc`/`mimalloc`（或 `#[global_allocator]`）：aog 形状库 burst 分配场景下比默认系统分配器稳（避免 swap 抖动导致 deadline 不触发，见 `17`）。**低成本高回报**。
- `Cargo.toml`：`lto = "fat"`、`codegen-units = 1`、`[profile.release] opt-level = 3`、`target-cpu=native`。`RUSTFLAGS="-C target-cpu=native"` 对 flood-fill 密集循环常有 10–20% 提升。
- 热点函数 `#[inline]` / `#[cold]` 标注（deadline 检查、错误路径）。

## 7. ⭐ 实验方法论与基准纪律（本文补遗）

> 当前基准的「单题耗时」读数**被系统性高估 4×**，会误导所有优化评估。

### 7.1 `RUST_PARTS=4` 墙钟放大

`rust_solver._wall_budget`（`rust_solver.py:167`）= `RUST_PARTS(4) × timeout × 1.2`。即 Python 给子进程的墙钟 = 4×timeout。原因：Rust 串行跑 4 个模块各拿 timeout。**这导致**：
- benchmark 报告的 `elapsed_ms` 是「子进程墙钟」，含前面模块耗尽的 timeout，**不能反映「真正解出的模块」的 CPU 时间**。
- §4.1 并发改造后，`RUST_PARTS` 应改为 `1`（模块抢同一时钟），耗时读数才真实，**且会立刻让很多「超时题」变成「在 timeout 内解出」**。

**建议**：并发改造落地时，把 `_wall_budget` 改为 `timeout × 1.2`（去掉 ×4），并让 `attempts` 字段报告**每个模块的独立 elapsed**（已有字段，直接读它评估优化）。

### 7.2 确定性 / 可复现

- 当前搜索依赖 deadline 墙钟 → 同题同机两次可能走不同深度（非确定性）。优化评估须：
  - 用 `attempts` 的 per-module status 而非总耗时做「是否改进」判据（耗时受 CPU 争抢噪声大）。
  - 引入 `--retry-timeouts` 单独确认 borderline（已有）。
- ML/并行改造会进一步降低确定性；需固定 seed + 记录 `RNG_SEED` 到 `attempts`。

### 7.3 评估协议（建议固化）

每次优化提交必须附：
1. `results/bench/<日期>_<sha>_<msg>.txt`（全量，AGENTS.md 已要求）。
2. 与上一基线的 **REGRESSION/NEW** 对比（`--baseline` 已支持）。
3. 注明 **单一模块 CPU 耗时**（非放大后的墙钟）。
4. 若改路由/并发，**单独报告「并发前/后」解出数**，隔离「算法改进」与「预算利用率改进」。

## 11. ⭐ 进一步全新方向（未被前 23 篇与 §4–§7 覆盖）

> 本节是本文对「新方向」的**主干贡献**。下面每条都未在 `docs/优化/` 前 23 篇出现，也不属于 §4–§7 已展开的四类。每条按「原理 → 本题适用性 → 落地位置 → 收益/风险/工作量」给出，并标注与现有代码的接口点。目标是给下一轮优化提供**未被开采的矿**。

### 11.1 增量 / 交互式求解（UI 实时重解）

- **原理**：当前每次求解都是「整盘从头 DFS」（`solver_runner` / `rust_solver.solve`）。但在 UI 里用户边画边界、边加线索，**每次改动只影响局部**。可维护一棵「已固定的部分赋值 + 约束图」，仅对变更区域做局部重传播 / 局部重搜索，复用未受影响子树的结论。
- **适用性**：`grid_widget` 实时刷新（`properties_panel.board_modified` → `grid_widget.update()`）目前只刷新显示，不重解。把"重解"也增量化为交互体验的直接升级。
- **落地**：在 `rsolver` 暴露 `solve_incremental(prev_state, delta)`；`prev_state` = 上次的 `cell_to_region` + 形状库 + 传播固定点，`delta` = 新增的 `is_boundary`/线索。
- **收益**：交互延迟从 O(全搜索) → O(局部)。对大网格手绘体验质变。
- **风险**：中（增量正确性需保证；可退化为全解作兜底）。**工作量**：中。

### 11.2 更快的序列化协议（IO 热路径）

- **原理**：子进程协议是 `serde_json` 全量 parse + 每行 JSON（`io.rs` / `rust_solver.py`）。2488 题批量时，JSON 编解码本身占可观墙钟；`puzzle_to_dict`（`rust_solver.py:171`）也是 Python 侧开销。
- **新方向**：① 子进程内用 `simd-json`（serde 兼容）或 `ryu`/二进制；② Python↔Rust 改用 **内存映射 / 共享内存 + flatbuffer**，避免两次 JSON 往返；③ `--batch` 已复用子进程（`P2 #7`），但每行仍 JSON — 换二进制帧后吞吐再上一层。
- **收益**：批量基准（CI 每日跑）墙钟降 10–30%（纯 IO，不改算法）。
- **风险**：低（协议兼容性）。**工作量**：小。

### 11.3 增量验证（只验变更区域）

- **原理**：`validate::validate`（`validate.rs:14`）每次**全量扫 22 条规则**。但 `build_solution`（`mod.rs:291`）出口若已知"仅第 k 个区域是本次新定的"，只需验证该区域 + 其邻接边/顶点/邻居区域，复杂度 O(变更区域) 而非 O(HW)。
- **适用性**：aog 逐区域构造（`search.rs`）、`reconstruct_and_validate`（`pieces.rs:590`）天然带"本次新增区域"信息 — 直接喂给增量验证。
- **收益**：去掉 §6.3 的"双重全量 validate"后，进一步把"单次全量"降为"增量"，对秒级题与批量 CI 显著。
- **风险**：低（正确性由最终全量兜底）。**工作量**：小。

### 11.4 位并行 flood-fill / 连通性 SIMD

- **原理**：§6.2 用 `u32` region id 降内存；更进一步 — 把整盘 cell/edge 状态打包成 `u64`×N 位向量，**一条 SIMD 指令同时推进多格的连通传播 / 边界度统计**。`empty_area_check`（`search.rs:1265`，每放置一次全盘 flood-fill，O(cells²) 热点）、`is_connected`（`validate.rs:393`）都可用位并行重写。
- **适用性**：网格 ≤16×16 → 256 格，4 个 `u64` 即可整盘位图；auto-vectorization 友好。
- **收益**：连通性检查常数因子数量级下降（aog 主热点）。
- **风险**：中（位运算正确性需小心边界）。**工作量**：中。

### 11.5 主动降维 / 边界推断驱动的分治（比 §3.6 更深）

- **原理**：§3.6 的降维分解依赖"已有确定边界分隔"。新方向：在预搜索阶段**主动推断边界**以最大化分解 — 用 compass 边界框（§3.7）、ring/brick 顶点度传播（§11.6）、watchtower 双触碰（引 `21` 补挖）先把尽可能多边"钉死"为 Boundary/NonBoundary，再把网格切成多个**互不连通子网格**分别求解后拼回。即"deduction engine 的副产品 = 分解切分"。
- **适用性**：对 13×13+ 大网格（档⑤）尤其关键 — 切两半复杂度从 O(2^256) → O(2^128)+O(2^128)。
- **收益**：对抗天花板（档⑤）少数可用手段之一。
- **风险**：中（拼回时需保证跨切边界一致）。**工作量**：中–大。

### 11.6 预搜索"deduction engine"落到预搜索（统一传播到不动点）

- **原理**：`11` §3.3 已提出 `deduction_loop`（boundary→vertex→area→connectivity→forced→fence 六步传播到不动点），目前只零散实现（SAT 边界、BF 面积）。新方向：把整条循环**实现为预搜索阶段**，在 DFS 开始前尽量"钉死"确定信息，减少搜索树宽度。这是把 §3.7 的 6 条"建议增加"合成一个引擎。
- **适用性**：减少 aog/edge_csp 搜索空间的根因 —— 当前它们是"边搜边推"，改成"先推后搜"可显著降分支。
- **收益**：对多规则组合题（失败主因）是广谱提升。
- **风险**：中（传播顺序/不动点正确性）。**工作量**：中。

### 11.7 松弛求解 / 部分赋值 warm-start

- **原理**：先解一个"删除最难 1–2 条规则"的**松弛版**拿到大量已定区域，再把这些区域作为**固定初始赋值**喂给完整搜索（warm-start）。类似 SAT 的"core-first"。
- **适用性**：对"某条规则缺传播导致爆炸"（档②/③，如 compass+watchtower）特别有效 — 先忽略 watchtower 解出主体，再校验/微调。
- **收益**：把"全规则同时搜索"拆成"易规则定骨架 + 难规则微调"。
- **风险**：中（松弛解可能不满足难规则，需回退）。**工作量**：中。

### 11.8 随机化局部搜索求"任一解"（WalkSAT 风格快路径）

- **原理**：对唯一解谜题，随机初始化区域归属 → 迭代"翻转最小违反数的单元格/边"（min-conflict / WalkSAT）→ 常比 DFS 更快撞到解。作为**快路径先试**，失败再退回 DFS。
- **适用性**：大网格、约束较松的题（档⑤ 部分）；不保证唯一性但官方题唯一解，撞到即正确。
- **收益**：对"DFS 分支爆炸但解其实稠密"的题是潜在数量级加速。
- **风险**：低（不影响正确性，仅多一条候选路径，进 §4.1 并发跑）。**工作量**：小–中。

### 11.9 跨机 / GPU 分布式穷举（对抗档⑤天花板）

- **原理**：1434 类"参考求解器也解不动"的题，单核无解。把"形状放置候选 × 子区域划分"分发到多机（或 GPU）做穷举/验证。§4.4 指出纯 GPU 不划算，但**对形状库枚举 / 候选生成**（无依赖、规则一致）GPU/分布式是真并行。
- **适用性**：仅档⑤ 极端题；工程重，是"天花板突破"的最后手段。
- **收益**：可能解锁当前 0 解出的 ~40 道根本难题中的一部分。
- **风险**：高（工程、确定性、成本）。**工作量**：大。

### 11.10 求解器形式化验证 + 差分模糊测试（robustness 方向）

- **原理**：`17` 指出 deadline 盲区与挂死（"LB:sealed" 根因是 HashMap 非确定）。新方向：① 构造**差分测试**（Rust 求解器 vs 参考求解器 / vs 自身确定性种子）自动抓"剪枝误杀正确解"；② 用 fuzzing（随机 puzzle + 边界组合）找非终止/崩溃；③ 对关键剪枝（sealed-region、vertex ring/brick）做**不变量证明**（"该剪枝永不放过任何解"）。
- **适用性**：保证"加任意新优化不引入回归"（当前靠全量 benchmark 兜底，慢且噪声大）。
- **收益**：把"优化→全量回归"的 30 分钟循环，前置为"单元级差分 + fuzz"秒级。
- **风险**：低（纯测试基建）。**工作量**：中。

### 11.11 编译式特化（puzzle-specific 部分求值 / JIT）

- **原理**：每道 puzzle 的 22 规则在搜索中是"if rule_present {…}"分支 + 泛型。可把**具体 puzzle 的约束编译成一段特化代码/字节码**（partial evaluation），去掉所有"规则是否存在"的判断与数据泛型，类似 SQLite prepared statement。
- **适用性**：对**重复求解同题**（benchmark 全量回归、CI、官方解比对）收益大 — 每题编译一次，跑多次。
- **收益**：热路径分支预测 + 内联友好，常数因子 10–30%。
- **风险**：中（特化器本身需维护）。**工作量**：大。

### 11.12 语料级记忆化 / 共享预计算

- **原理**：① aog 形状库（`shapes.rs`）每题重建 → 跨 2488 题**共享一个持久化 shape 数据库**（mmap）；② **解缓存**：puzzle 内容 hash → 直接返回已知解（CI/benchmark 重复跑同题零成本）；③ polyomino/dihedral 表一次性生成共享。
- **适用性**：批量基准（每日跑、回归 `--baseline`）重复同题极多 → 缓存命中率高。
- **收益**：批量墙钟大幅下降 + aog 启动形状库构建成本摊零。
- **风险**：低（缓存键含全部线索/边界才命中）。**工作量**：小–中。

### 11.13 ML 深化：GNN / RL / Transformer 策略

- **原理**（深化 §5）：① **GNN** over grid graph 预测"每格的区域连通性 / 形状类别"，替代手写 flood-fill 启发；② **RL（PPO）** 学 DFS 长程分支策略（比 §5.2 梯度提升更适配信用分配）；③ **Transformer** 把"谜题 → 模块执行序列"当序列决策（序列到序列）。
- **适用性**：2488 题监督信号充足；档③/⑤ 硬题最可能受益。
- **收益**：潜在把手写启发式升到"问题自适应"级别。
- **风险**：高（需轨迹采集、训练管线、防过拟合）。**工作量**：大。

### 11.14 自适应预算分配（learned per-module budget）

- **原理**（深化 §5.1 + §4.1）：并发均分预算仍浪费。用模型给"最可能解出"的模块**动态多给预算**、弱模块少给 —— 比"并发均分"更聪明，且直接降墙钟。
- **适用性**：配合 §4.1 并发改造天然落地（预算本就是共享时钟）。
- **收益**：在并发基础上再砍无效墙钟。
- **风险**：低。**工作量**：小（复用 §5.1 模型）。
